# 栖灯镇：美术与资产标准

这份文档规定资产的风格、尺度、交付内容和验收办法，给做资产的人（主要是 Antigravity）和集成的人（Claude）共用。已有的约定不在这里重写，只指过去：

- 导出约定（单位、坐标、原点、缩放、动作命名）：`client/art_source/README.md`。那里的「骨骼命名」一条还是旧 Mini Characters 时代的，和现在的 KayKit 骨架不符，以 `client/ASSETS.md` 的「居民模型的实测属性」为准，标准件任务（T02）里一并改掉。
- 素材许可台账和再生成命令：`client/ASSETS.md`
- 外观表、私有覆盖目录、画质开关：`client/README.md` 的「美术层与可替换素材」

来源：2026-11-15《栖灯镇开发协作与制作规范 v1.0》第 7、8、13、14 章，经评审后收进仓库。标了「待样板验证」的数字是起点，不是定论；样板通过后把实测值写回这里。

## 方向（主人已定，不重新讨论）

《牧场物语：重聚矿石镇》的生活感，加《织梦岛》重制版的微缩场景感。约三头身；木结构、瓦顶、暖帘；米白、木棕、灰蓝屋顶、柔和绿，少量暖橙灯光；材质简洁柔和；固定斜俯视；白天要好看，傍晚点灯是特色。保持三维，不做 HD-2D。目标是「让人愿意在里面闲逛、坐下、聊天」。

材料关系用木、石、陶、织物和纸灯统一。建筑的用途靠体块、门头、内部布局和专属道具认出来，不靠给同一种房子换颜色。

## 许可

- 进这个公开仓库的素材只能是 CC0，或者完全自制（自制的在台账里写「自制」和制作脚本）。
- 不允许再分发的素材只放主人的私人云盘和 git 忽略的 `client/town/art_private/`。
- 每个包、每件自制资产都记进 `client/ASSETS.md`：来源地址、版本、取得日期、许可、sha256、做过的修改。
- 生成的图片只能当概念参考或纹理草稿；要进游戏，先过尺寸、接缝、来源授权和实机清晰度四项检查，并在台账里写明是生成的。

## 尺度、坐标和通行

- 1 个单位是 1 米；轴向、原点、缩放照 `client/art_source/README.md`。轴向转换只在导出脚本里做，不许每件资产手工补偿。
- 固定物的原点在落地处的底面中心；门在铰链；手里拿的东西在握点。
- 建筑模块按 0.5 米的格子组织（和服务端网格 `cell: 0.5` 一致）。
- 门、走道和使用位够不够宽，用角色半径和服务端网格验证（`spatial/compile.ts`），不用眼睛估。
- 资产不决定碰撞和可走范围。服务端地图里声明的脚印和使用位才算数；模型做大了挡住路，是模型的问题。

## 布局从哪里来（主人已定）

布局的唯一来源是服务端的地图数据文件（现在是 `packages/engine/src/world/spatial/town-map.ts`），由 agent 直接改数据，发布后不原地改，动了可走范围、落脚点或物件位置就换 `mapVersion`。**不做「Godot 场景导出布局」的工具链。**

- 资产包可以带一份「建议摆法」的样例，只是参考，不是权威坐标。
- 纯装饰（不挡路、没有交互）的摆放现在在客户端的 `town_layout.gd` 里，`world.gd` 会拿服务端地图校验脚印。新街区的装饰是继续放客户端，还是并进地图数据，在首区灰盒（T03）时定，定了写回这里。
- 同一处坐标不许两边各存一份、各改各的。

## 材质、贴图和预算

- 维护共用的材质和色板，控制高光、饱和度和夜里的对比。同一种材料用同一个纹理尺度和方向。现在的做法是城镇着色器采样调色板贴图、无高光，新资产先沿用。
- 细节按物件在默认镜头里占多大屏幕来分配。色板、图标、近景材质分开处理，不统一升成大贴图。
- 预算按四类分别记：普通道具、建筑、角色、地标。每类记三角形数、材质槽数、贴图尺寸、动画数。**数字待样板验证**：标准件在选定的最低设备上跑过之后冻结，冻结前不写「性能通过」。
- 渲染器是 Godot 4.7 的 Compatibility（WebGL 2），单线程网页导出。做效果之前先确认这个渲染器支持。

## 动画

- 骨架和现有动作沿用台账里的 KayKit Rig_Medium 和 `residents_anims.res`；新动作重定向到同一副骨架，命名照 `client/art_source/README.md`。
- 首区要补的动作：取、放、切配、用工具、递交。每个动作标出事件点（比如「刀落下」「东西离手」），客户端在服务端确认的状态上播放，不自己猜进度。
- 待机动作不带社交含义。挥手、递东西这类动作只在服务端确认了对应的真实行动之后播放。
- 现在角色手上没有挂点：生成脚本删掉了武器和道具节点，也剥掉了动画里的 `handslot` 轨道（`client/art_source/build_residents.gd`）。要让角色手里拿东西，得从生成脚本改起并重跑，需要 KayKit 的原始压缩包。

## 一个资产包要交什么

验收看的是「另一个人能不能重新导出、重新导入、在游戏里用起来」，不数模型文件有多少。

**T02a 已把这条链走通并写定了契约**（节点命名、颜色约定、清单字段、命令、「怎么做一件新资产」）：见 `client/docs/T02a.md`，那里是唯一的权威写法，这里不重复。机器校验：`npm run client:assets:check`；重建：`npm run client:assets:build`。

| 部分 | 内容 | 放哪里 |
|---|---|---|
| 源 | 制作和导出脚本；手工做的 Blender 源文件；纹理和声音的源文件 | `client/art_source/`（功能物件和建筑在 `kits/<套件>/<资产编号>/`） |
| 运行资源 | GLB、贴图、声音、图标 | `client/town/assets/`（功能物件和建筑在 `kits/<套件>/<资产编号>/`） |
| 包装场景 | Godot 场景，带资源引用、遮挡淡出的部件、动画接口、局部锚点 | 和 GLB 同目录（`<资产编号>.tscn`，由脚本生成不手改） |
| 清单 | 稳定的资产编号、版本、尺寸、材质槽、状态列表、锚点列表、依赖、来源和许可 | 和包装场景放一起；许可同时记进 `client/ASSETS.md` |
| 验证记录 | 导入结果、固定镜头的原始截图、实际操作记录、预算统计、已知限制 | `client/docs/` |

源文件的规矩：

- 能用脚本生成的优先交脚本，脚本要能从头重跑出同样的结果。
- 手工做的 `.blend` 可以进仓库，但单个文件先控制在几 MB 以内；超过了先问，再决定用 Git LFS 还是放仓库外并在台账里记校验值。不许为了这个改写仓库历史。
- 同一个二进制源文件同一时间只有一个人改。

## 静态装饰和功能物件分开

- **静态装饰**（花草、石块、重复的路边物件）：继续走批量实例化，只要网格。
- **功能物件**（门、灶台、能修的灯、座椅）：保留完整的 Godot 包装场景，对外给出状态和动画接口。现在的装饰加载只提取网格，带动画的 GLB 导进来不会自动有交互；接通「按服务端状态切外观」的入口已在 T02a 做完（`stateful_prop.gd`，外观表的 `scene` 条目，见 `client/docs/T02a.md`）。
- 资产只声明它有哪些状态和锚点。什么时候进哪个状态、耗什么、产出什么，由服务端规则决定。模型上的脚本不许结算奖励、改库存或放宽权限。

### 以灶台为例的交付标准

- 外观分得清空闲、使用中、完成、异常四种状态，默认镜头和最近的缩放下都认得出来。
- 局部数据：碰撞占地、玩家使用锚点、物品放置锚点、特效位置、遮挡设置。
- 声音、图标、提示文字和状态名一起交。客户端只按服务端给的状态切换表现。
- 验证：门口和工位走得到；多人不会站进同一个保留位；重新导入之后材质、锚点和动画引用都还在。

## 先做标准件，再批量做

先做一组在实际镜头下成立的标准件：一段墙、一个门洞、一张桌子、一盏灯、一个角色、一套地面。用它锁定轮廓、尺度、材料和明暗，再批量做。

现状（2026-11-15 核对）：仓库里没有任何 `.blend` 文件，也没有用 Blender 的脚本（`recolor_*.py` 用的是 Pillow）；街景建筑是 `town_art.gd` 程序生成的，道具是 Kenney 的模型改色。所以「Blender 源文件到 GLB」这一段是从零开始，标准件任务要把它第一次走通。

Antigravity 的第一个任务是厨房的一个标准工位。**退路写在前面**：样件在实际镜头下不过关（轮廓、风格统一、状态可辨其中任何一项），就不继续让它从零建模，改成用现有的 CC0 素材包（Kenney Fantasy Town、KayKit）改色、拼装、加程序生成的配件，这条路仓库里已经走通过（`recolor_kenney.py`、`recolor_residents.py`、`town_art.gd`）。走哪条路由主人看过样件之后定。

**现状（2026-11-15 夜）**：样件交了，是公共厨房的砖砌双眼灶台 `kitchen/stove_station`（记录在 `client/docs/T02b.md`，实际镜头的对照条在 `client/docs/T02/shots/kitchen/`）。它只在 `?debug=1&props=kitchen` 下出现，没有进默认的外观表。过不过关、走自建还是 CC0 拼装，等主人看图定。

## 图形验证

- 报告里分开标：静态检查、无界面导入、编辑器运行、真实浏览器运行、真实移动设备。没做的那一层写「待验证」。
- 软件渲染（无头 Chromium）的截图只能证明「画出来了、位置对」，不能当清晰度或性能的依据。
- 清晰度的对照：同一台设备、浏览器、镜头、位置、时间和人数下，分别截固定渲染比例 1.0、自动档、低档的原始 PNG；记下画布尺寸、设备像素比、实际的内部渲染尺寸和画质设置。
- 固定镜头至少覆盖：默认视角、最近的缩放、夜里、室内。
- 不拿效果图、旧截图或别的构建的截图填验证记录；截图和操作记录要对应同一个提交。
