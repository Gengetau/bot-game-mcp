## 本轮跑端到端时发现并修掉的客户端问题

- **主动离开后，在途的心跳会让页面自己重新进入**（`main.gd` 的 `_heartbeat`，步骤 14 四遍里有一遍逮到）：离开的瞬间如果恰有一次心跳在路上，
  服务器回 422 `presence_lost`，旧代码把它当成「在场租约丢了（睡了很久）」立刻 `POST /enter`，抢在 WebSocket 的撤销通知前面把居民重新放回镇上，
  页面也不会停在「已离开」。现在先等 2 秒，期间收到撤销（`revoke_checking`）或已进入离开状态就放弃重新进入；真正的租约丢失只多等 2 秒。
  这是偶发竞态（改前 4 遍完整运行里出现 1 次），没有做到「改前必现、改后必不现」的对照；改后连续两遍完整运行都通过。

## 外人走 README 时发现并已处理的问题

1. **README 的启动命令走不通**：`BOTGAME_TOWN_CLIENT_DIR=client/town/build/web` 是相对路径，而 `npm run dev -w bot-game-mcp` 会先切到 `packages/engine`，
   目录就指到了不存在的地方，页面是 404「三维客户端还没有部署」。已改成 `"$PWD/client/town/build/web"` 并在 README 里写明原因。
2. **别人进镇、离开时页面不更新**（服务端只在有人走动时推场景快照，见「给服务端的发现」）：A 登录后 B 的页面一直看不到 A，直到 A 走动。
   当时客户端加了兜底（WebSocket 通着时每 3 秒再取一次 `GET /scene`）；服务端补上推送之后兜底已经去掉，去掉后本脚本重跑全过。
3. **兜底带来的一个竞态（已修；兜底去掉后这道防护仍保留，断线时的轮询回应同样可能晚到）**：晚到的旧 `GET /scene` 回应会盖掉 WebSocket 刚推来的新快照，把刚开始走的人「按回原地」冻结最多 3 秒。
   本脚本第一次完整跑就逮到了（步骤 2 / 8 偏差 7 到 8 米，线性增长）。已在 `_on_scene` 里丢弃 `serverTime` 比已应用的更老的快照。
4. **断线只有一个会闪的小点**：断线时界面没有文字，用户和截图都看不出来「重连中」。已在连接状态点旁加文字「重连中…」/「离线」（`#connText`）。

## 给服务端的发现（已修）

> 这一条随后已在服务端修掉：上线、离线、在场租约到期、改名、进出小游戏都会通知同一场景实例（`space.ts` 的 `touchScene`，带测试），客户端的 3 秒兜底也已去掉。下面保留当时的记录。

**场景快照的 WebSocket 推送不覆盖「有人进镇或离开」**。复现：开两个页面（或一个页面加一个 MCP AI 居民）进同一个场景，让其中一个进镇后站着不动，
另一个的页面里一直看不到它（`actors` 里没有），直到它第一次走动。原因：`packages/engine/src/world/service.ts` 的 `bumpSpace()` 只被 `space.ts` 里位置和导航变化的路径调用
（`space.ts` 约第 254、263、315、341、465、746 行），`enterWorld` 把居民置为在场（`present_since`）、离开、离线、被请出等不调用它，而 `sceneView`
又按 `present_since` 过滤在场的人。建议在在场状态变化（进入、离开、租约全部过期转离线、恢复在场）时对该居民所在的场景实例 `bumpSpace`。
修好后客户端的 3 秒兜底可以去掉（`main.gd` 的 `SAFETY_POLL_MS`）。

## 没能验证的事项

- **真机**：安卓 Chrome、iOS Safari（含 `connect-src` 同源 ws 在旧 Safari 的行为、音频手势、安全区）、Windows Chrome / Edge 都没有测。
- **Firefox、WebKit**：容器里没有。
- **声音**：步骤 1 断言点进入之后至少有一个 AudioContext 是 running，但无头 Chromium 在点进入之前就已经是 running（不拦自动播放），所以没有验证「被浏览器拦住、靠用户手势解锁」这条路径，也没有验证 iOS 的 `interrupted`；没有听过音量和脚步声的效果。
- **帧率、功耗、内存、弱网**：软件渲染没有参考意义；没做弱网或丢包模拟。
- **高分屏的 3D 降分辨率**：只在无头环境见过（桌面 dsf 2 会触发），真机效果没测。
- **后台标签页**：浏览器暂停渲染循环后心跳和续租也暂停（在场租约 60 秒），回前台重新进入；本脚本没有覆盖。
- **iOS 音频 `interrupted` 状态、真机软键盘、读屏软件、`BroadcastChannel` 退路（无 Web Locks 的浏览器）**：客户端同事改了但只在 Chromium 里验证了一部分，端到端没有覆盖。
- **登录失效（会话被撤销）后的「重新登录」面板**、**回前台后的死连接探测**：没有加进端到端（需要改会话或模拟页面可见性，不稳定），只有「静默 12 秒」这条路径有覆盖。
- **登录票据兑换（非开发登录）流程**：脚本只用开发登录。
- **真实模型驱动的 AI 居民**：步骤 8 已经用 `ResidentRunner` 驱动（决策函数写死、不调用模型），验证了运行器自动续租、模型不参与沿路控制；没有接真实模型，也没有覆盖运行器的聊天、报价、小游戏等其他路径。

## 已知的小问题（不影响验收，没有改）

- **软件渲染下页面时钟比服务器慢约 110 到 290 毫秒**（步骤 2、8 的对时数据，每遍都是负值；最后一遍 12 个样本在 -113 到 -250 毫秒之间，更早的几遍到过 -285）。原因推断：渲染帧只有 3 到 8 帧每秒，WebSocket 的 pong 要等下一帧才被 `poll` 到，
  「收到时刻」晚了半帧到一帧，往返被算大、偏移被算小。这是推断，没有单独验证。真机 60 帧时这一项应该小一个数量级（待真机）。
  对时断言的容差定为 ±400 毫秒（见下），位置断言（0.6 米）只比较「页面位置」和「用页面自己的时钟现算的折线位置」，所以抓不到这个系统性偏差；
  它折算成位置约 0.3 到 0.7 米的整体滞后（走路 2.4 米每秒），渲染饥饿的环境里是真实存在的。
- **对时断言的容差 ±400 毫秒的依据**：更早实测三遍共 36 个样本全部在 -285 到 -102 毫秒之间，最后一遍的 12 个在 -250 到 -113 毫秒之间；读取页面 `serverNow` 的时刻有 140 到 250 毫秒的不确定（评估一次页面脚本的耗时），
  已用「值变化的那一刻」对齐，剩下的不确定度折进这个容差；再宽就失去意义（400 毫秒 = 近 1 米）。
- 位置精度断言的容差是 0.6 米：走路速度 2.4 米每秒，约 250 毫秒；正常的采样误差在几厘米到 0.3 米，超过 0.6 米说明页面没有拿到或没有应用服务器的折线。
- 点按位移阈值的断言（步骤 7）在 CDP 里把整段触摸手势一次发出：渲染饥饿时每条触摸命令要 0.4 到 0.5 秒才应答，逐条发会超过客户端的 700 毫秒点按时限，测到的就不是位移阈值。
  这条断言没有对着「旧的 14 物理像素阈值」验证过会失败（没有去回退客户端重导出）。
