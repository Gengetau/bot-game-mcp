# T01：清晰度基线

画面在一部分设备上发糊。这一段先把「清晰度策略」做成可测的纯逻辑、补上诊断读数、去掉待机时的随机挥手，并给出一个固定镜头的对照脚本，等真机对照图出来再决定要不要动别的东西（比如地面烘焙分辨率 `BAKE_PPM`，这一段没有碰）。

## 1. 文件

| 文件 | 作用 |
|---|---|
| `client/town/scripts/quality_logic.gd` | 清晰度策略的纯逻辑：三个档位、动态分辨率的升降和防抖、像素上限、调试覆盖 |
| `client/town/scripts/main.gd`（画质和调试信息部分） | 每帧喂 dt 和像素数、把结果写给 `scaling_3d_scale` 和阴影开关；`__town` 新字段 |
| `client/town/scripts/bridge.gd` | 读 `scale=`、`zoom=` 两个调试参数（和 `hour=` 同样的读法，只在 `debug=1` 下生效） |
| `client/town/scripts/actor.gd` | 待机不再随机挥手 / 互动，改成偶尔换 `idle2` |
| `client/town/web/hud.js`、`shell.html`、`hud.css` | 「画质」三态按钮；告知 Godot 是不是软件渲染 |
| `client/tests/quality_logic_test.gd` | 单测（60 项） |
| `scripts/client-shots.mjs` | 固定镜头对照脚本，`npm run client:shots` |

## 2. 规则

- 档位：`auto`（默认）、`high`、`low`。网页层存 `localStorage` 的 `town3d.quality`；旧的 `high` / `low` 照字面沿用，没存过是 `auto`。
- `high`：渲染比例固定为像素上限允许的最大值，开阴影。`low`：固定 0.6（再受像素上限约束），关阴影、脚底圆影。`auto`：阴影沿用原来的默认（触屏和软件渲染关，其余开），渲染比例动态调整。
- 像素上限：画面超过 250 万像素时按 `sqrt(250万 / 像素)` 封顶，三个档位都受它约束；`__town.scaleCapped` 为真表示被它压低了。
- auto 的动态比例贴着像素上限走：上限以上那一截本来就没生效，每帧先压到上限上再谈升降。不压的话，高分屏上头几次「降档」一个像素都没少，会被「降了没用就不降」当成没用，从此降不到上限以下（评审发现，有单测）。切档位或改调试覆盖时丢掉正在进行的探测，不拿切走之前的帧率当基准。
- `auto` 的下限：正常设备 0.5；软件渲染（`hud.js` 用 `WEBGL_debug_renderer_info` 判断，经 `gpu` 事件告诉 Godot）0.3，免得无头浏览器的端到端变慢。
- 降：平均帧率低于 24 降一档（乘 0.85）；单帧超过 0.35 秒立刻降一档（乘 0.7）。每 1.5 秒检查一次。
- 升：不再用固定的 52 帧。「这台设备能到的帧率」估计 = 平滑帧率的衰减最大值（衰减时间常数 45 秒），下限 30；平均帧率达到估计的 90%，并且连续两个检查周期都满足，才升一档（乘 1.08）。锁 30 帧的手机估计就是 30，能升回去。
- 防抖：升上去之后 6 秒内又被降，就把升之前的那一档记成暂时的上限，60 秒后再试，每次失败翻倍，封顶 300 秒。升成功并稳住 6 秒后清掉记录，退避回到 60 秒。
- **降了没用就不降**（实机对照之后加的，见第 5 节）：从开始降的那一档算起，比例降到 73% 以下（像素少了一半），帧率却没涨到该涨的两成（约 1.18 倍），说明瓶颈不在像素上（显卡被别的程序占着、CPU 忙）。这时回到开始降之前的那一档，120 秒内不再降（单帧过长也不降），到期再试，每次再犯翻倍，封顶 10 分钟；哪一次降下来有用，时长回到 120 秒。帧率用检查周期里实数出来的，不用平滑值。软件渲染不做这个判定（那里画得慢就是像素多，端到端也跑在上面）。`__town.drsHold` 为真表示正处在「不再降」的时段里。
- 常量都是 `quality_logic.gd` 顶部的具名常量，理由在注释里。
- **取舍（自动档偏向清晰）**：自动档的目标是「不低于约 24 帧的前提下尽量清晰」，不是「尽量跑满刷新率」。一台 60 帧屏的设备如果满分辨率只有 30 帧上下，能力估计会在一两分钟里衰减到 30 左右，然后稳在高分辨率、30 帧；想要更顺的人切到「低」。理由：这个游戏是点地走路、看字和看小物件，糊比略低的帧率更伤；而且原来的毛病正是「降下去就回不来」。帧率底线仍是 24（低于它一定降）。

## 3. 调试与诊断（`?debug=1`）

- `?debug=1&scale=0.75`：固定渲染比例（限制在 0.3～1.0，仍受像素上限约束）；`?debug=1&zoom=12`：固定镜头距离（限制在 6.5～36 米，每帧压回，滚轮和双指缩放改不动它）。
- `window.__town` 新增：`renderScale`（视口实际的 `scaling_3d_scale`）、`renderSize`（`[宽, 高]`，内部 3D 渲染的像素尺寸）、`canvasSize`（`[宽, 高]`，画布物理像素）、`qualityMode`（`auto` / `high` / `low`）、`drsFloor`、`drsCeil`（没有暂时上限时为 1）、`drsHold`（降了没用、暂时不再降）、`fpsAvg`（策略用的平滑帧率）。另有 `scaleCapped`、`debugScale`、`softGpu`。原来的 `quality`（阴影高低）、`drs` 保留原含义。

## 4. 待机动作

居民站着不动时不再随机播放 `wave` / `interact`（挥手这类社交动作只能由玩家的真实指令触发）。改成每隔十几秒播 3.5 秒 `idle2`（KayKit 的 Idle_B，已在 `residents_anims.res` 里确认存在）再回 `idle`。`play_once("wave")` 这类由真实事件触发的调用保留。NPC 在读书姿态（`kind == "npc"` 且 `pose == "read"`，C6 加的特例）时不换 `idle2`，书本的显隐照旧；坐着时本来就不进待机分支（`_sit_phase != 0`）。

## 5. 怎么验证

- `bash client/tools/unit.sh`（无头 Godot，含 `quality_logic_test.gd`）、`npm run client:lint`。
- 「锁 30 帧的设备降档后能升回去」这条单测：先在旧规则（平均帧率高于 52 才升）下确认是红的，再换成新规则变绿。
- 实机：`npm run client:export` 之后 `npm run client:shots`（真实 Chrome 有头），看 `client/docs/T01/shots/results.json` 里每个组合的 `renderScale`、`renderSize`、帧率，和拼好的对照条 `strip.png`（每格是那张图正中 480x300 的原始像素）。

## 6. 实机对照（2026-11-15 夜，主人的电脑）

设备：Windows 11，AMD Ryzen 9 7940H，Chrome 157 用的是核显 AMD Radeon 780M（ANGLE / Direct3D 11），窗口 1440x900，设备像素比 1，显示器刷新率高于 60。

**最要紧的发现：这台机器上帧率低不是因为像素多。** 第一轮对照，固定 1.0 和自动档降到 0.5 的帧率一样，都是 8 到 9 帧；低档（0.6、不开阴影）也只有 11 帧。追下去：

- 同一个 Chrome 里空白页是 155 帧，进镇之前的面板是 161 帧，进镇之后 8 帧；每帧只有约 200 次绘制、12 万个三角形，没有大的贴图上传。
- 一帧里几乎全部时间花在 WebGL 的一次同步调用上（`getParameter`），也就是在等显卡把这一帧画完。
- 系统的显卡计数器：动态壁纸程序（Wallpaper Engine）占着这块核显 3D 引擎的 70% 到 96%，Chrome 只分到 17% 左右。窗口最大化也一样。
- 壁纸不占显卡的那些时候（同一晚后面几轮），同样的画面在 1.0、阴影全开下是 57 到 60 帧。

所以以前「画面发糊」在这台机器上的来历是：帧率被别的程序压到 10 帧以下，旧规则见帧率低就把渲染比例一路降到 0.3，画面糊了，帧率一点没涨，而且升不回来。
T01 原来的规则（下限 0.5、能升回）只是把糊的程度减轻；补上「降了没用就不降」之后，这种情况下画面保持原来的清晰度，每隔几分钟花四五秒再试一次。
壁纸程序本身游戏管不了：想要帧率，得在壁纸程序里设成「别的程序在前台时暂停」。

最后一轮的数据（提交和每一行的读数在 `results.json`；这一轮壁纸大部分时间没占显卡，头一行和低档的后两行受了同时在跑的别的任务影响，帧率只当参考）：

| 镜头 | 固定 1.0 | 自动 | 低（0.6） |
|---|---|---|---|
| 默认视角（正午） | 1440x900，28.5 帧 | 比例 1.0，57.1 帧 | 864x540，52.6 帧 |
| 最近的缩放 | 50.7 帧 | 比例 1.0，58.9 帧 | 54.6 帧 |
| 夜里 21 点 | 57.1 帧 | 比例 1.0，57.3 帧 | 40.7 帧 |
| 室内（茶馆） | 59.8 帧 | 比例 1.0，59.9 帧 | 32.5 帧 |

看图的结论：

- 1.0 下人物、物件、地面的砖缝都是清楚的；低档（0.6）人物边缘有明显的锯齿和马赛克，是放大造成的，符合预期。
- 地面烘焙（`BAKE_PPM` 每米 32 像素）：默认视角下砖缝清楚；最近的缩放下砖缝发软，但人物是锐的，不构成「糊」的观感。**这一段不动它**，等首区扩图、要分块的时候（T08）一起看。
- 没有抗锯齿：1.0 下斜边有细锯齿，可以接受；要不要给「高」档加 MSAA，等性能预算定下来再说。

## 7. 没验证的

- 手机（触屏、高分屏、锁 30 帧）和别的显卡上没有跑过；`client/README.md` 的真机记录表仍是「待真机」。
- 「降了没用就不降」只有单测和推演：规则是看了第一轮对照的数据之后加的，加完之后的几轮壁纸程序正好没占显卡（自动档全程 1.0、57 帧以上），所以**显卡被占时它在实机上的表现还没有看到**；常量（73%、两成、120 秒）也没有标定。
- 顶栏三态按钮在手机宽度下的排版没有目测。
- 性能预算没有冻结：这台机器的帧率受壁纸程序影响太大，量出来的数不能当预算用。
