# C4：居民卡、当面邀请、会馆门牌与入户

本段把「人和人当面认识」这条主线在三维客户端里做通：点一个人出居民卡（名字、真人还是 AI、称号、个性、心情、简介），在卡上问对方爱好、邀请对方到自己家里做客；收到邀请的人看到提示并能一键去做客；灯巷会馆门前有门牌列表，进自己家、进受邀的家、没有邀请时看到明确的「需要主人的邀请」；进了屋有「屋里」信息和出门。报价、成交、送礼、还东西、写信、收回邀请的界面都不做（P2 或 C5）。

## 2. 钩子与归属（与跨段约定一致）

- `event_types`：`invite`、`asked_hobby`、`notice`、`you_arrived`。`on_event(ev)` 的载荷在 `ev.data`。
- `on_pick(kind, id)`：只认 `kind == "actor"`，且那个演员是 `human` / `agent`、不是自己。离自己（显示位置）不超过 `c4_person_reach()`（`/config` 的 `limits.personReach`，没有就 3.0 米）就当场出卡并返回 true；否则返回 false，main 照旧发 `navigate {approach}`。对「不是我的」一律返回 false。
- `actions(out)`：至多三个按钮，id 都以 `f:people:` 打头：`meet`（认识一下，副标题是最近那位的名字）、`visit`（去做客，副标题「某某的家」）、`doors`（门牌，只在灯巷会馆）。在小游戏里或只读时一个都不出。
- `tick`：自己节流到 4Hz（算最近的人、卡片近 / 远、自动关卡、待开卡的超时）；`notice` 的 120 毫秒去抖用累计的 dt，不用墙钟。
- 不实现 `blocks_input`、`tags`。
- 页签 `data-order="40"`；`host.setUnread` 的口径是「还没被看到的新请柬数」（`freshCount`；信里附的邀请在读信之后才出现在 `received` 里，同样算）。`debug()` 里有 `unread`。
- 不新增任何浏览器存储键。`host.open()` 只在玩家点了「门牌」按钮之后由 `feed("open")` 触发，收到邀请的事件里不开面板。

「点到的是谁、资料从哪来」集中在 `people.gd` 的两个函数：`_pickable(pid)`（能不能当「一个人」来点）和 `_profile_of(pid)`（卡上要显示什么）。**C6 接 NPC 时改这两处**：让 NPC 的演员在 `_pickable` 里返回 false（继续让给 C6 自己的菜单），或者在 `_profile_of` 里返回 NPC 的简化资料，并在网页一侧给 `card` 加一个 `npc` 类型（现在网页只认 `human` / `agent` 两种徽章）。其余部分不用动。

## 3. feed 协议（通道名 `people`）

`state`（`feed_state` 整份替换，相同内容不重复推）：

```
{ me:{id}, ctl:""|"readonly"|"game"|"offline", reach,
  card: null | {id,name,kind:"human"|"agent",busy,near,known,bio,traits[],titles[],mood,hobby:null|[名字],invited:null|{mins},walking},
  doors: null | [{home,ownerId,ownerName,ownerKind,lane,no,can,mine}],
  home:  null | {ownerName,ownerKind,mine,decor[],others:[{id,name,kind}]},
  invites:[{grantId,home,hostId,hostName,hostKind,mins,fresh}], freshCount }
```

`ack`：`{n, verb:"ask"|"invite"|"walk", id, ok, code, reason, message, retryMs, interests?, walking?, stale?}`。`n` 是网页发来的序号，Godot 原样带回，`debug().lastAck` 也存一份。`walk/arrived` 是「走到了」。`open`：网页收到就 `host.open()`。`reset`：离开 / 换人。

网页 -> Godot（`people.<name>`）：`close`、`ask`（JSON `{n,id}`）、`invite`、`visit`（home 编号）、`leave_home`、`dismiss`（grantId）、`seen`（页签被看到：清「未看」并刷新 /me）。

## 4. 行为要点

- 点人：近处立即出卡（不发请求）；远处 main 去 approach，`you_arrived`（`target.kind == "resident"`）之后开一个 3 秒的「待开卡」窗口，`tick` 里看距离不超过 reach + 0.5 米就出卡；超时 toast「走开了，再点一下 ta 走过去」。
- 卡的自动关闭：目标不在场景里、场景换了、进了小游戏、离自己超过 8 米且不在「走向 ta」状态、用户点 ✕ 或按 Esc。
- 问爱好 / 邀请走 `ctx.act_once`（不动 pending、不睡眠重试）。本地拦：只读、小游戏中、离线、对方在游戏里、同一动作在途、已邀请（`invites.sent` 或本次成功后记下的到期时间，到期后才能再邀请）。网络失败保留请求号，下次点同一个动作同一个人时带回，邀请不会多发一份。
- `too_far`：服务器给的 `navigateTo` 在错误体顶层；客户端只 `c4_approach`，不自动重发动作，到了之后卡上提示「到了，再点一次。」。
- 请柬：第一次 `on_me` 只入库不提醒；之后新出现的 `grantId`（`invite` 事件，或读信之后才出现在 `received` 里的）算新的，`actions` 里出现「去做客」，页签小圆点 / 角标 +1。「先不去」只在本页面把它从提示里收起，服务器没有拒绝邀请的动作，邀请仍然有效。
- 门牌和屋里每次都从当次 `/me` 现算，不累加；门牌上没有「在线 / 在家」之类的标记。`notice` 事件（例如邀请被收回）去抖 120 毫秒后刷新 /me。
- 进门 / 出门走 `ctx.c4_go`（main 的 `_do_navigate`）：自己家发 `{to:"home"}`，受邀的家发 `{to:"home:<编号>"}`，出门发 `{to:"residential"}`。不检查 `canEnter`，服务器是权威（强发会得到 422 `no_access`，由 main 弹服务器原话）。

## 7. 对规格的取舍与修正

- 「页签被看到」只清未读角标（`unseen`），不清 `fresh`：规格写「清 fresh」，但那样玩家一打开面板，请柬上的「先不去」按钮和「去做客」按钮就一起消失了，没法再点。现在：打开页签 -> 角标清零；点「先不去」或去做客 -> fresh 才清。
- 私宅的场所名：页面自己的 `spaceName` 来自地图表，私宅只写「家」；服务器的 `/me` 的 `location.name` / `here.name` 才是「某某的家」。端到端 60.6 以服务器为准。这是 main 的现状，没有改。
- 自己家的 navigate 用 `{to:"home"}`（不是 `home:<自己编号>`）。
- 60.9 的「抽屉开着」：卡片位置要跟着 `#bottombar` 被抬高而更新，`#bottombar` 自己的尺寸没变，`ResizeObserver` 看不到，所以另用 `MutationObserver` 看 `--dock-h` 与 body 属性。
- 手机抽屉里 `#dockGrip`（`dock.css`，C1a 拥有）盖住了整条页签（见下面「需要先合并的骨架补丁」）。

## 8. 需要先合并的骨架补丁 / 已知缺口

- **手机抽屉里页签点不到（骨架缺陷）**：`dock.css` 里 `#dockGrip { left: 0; right: 56px; top: 0; height: 44px; z-index: 2 }` 盖住了抽屉顶部的整条页签（`#dockTabs` 高 40px，页签在它里面），Playwright 报 `<div id="dockGrip"> intercepts pointer events`。C1a 只有一个页签所以没暴露；有两个以上页签时，手机上玩家点不了页签切换。本段没有改 `dock.css`（冻结），端到端里 `openPeopleTab` 对手机直接在 DOM 上 `click()`，并在代码注释里写明。建议统筹的 S1 补丁里把 `#dockGrip` 的 `top` 让到页签条之下，或者让 `#dockTabs` 的 `z-index` 高于 `#dockGrip`（页签条右侧仍留把手）。
- `personReach` 没有下发（`/config` 的 `limits` 没有）：现在读不到就用 3.0 米；S2 合并之后读 `limits.personReach`，客户端无需改动。
- 没有「拒绝邀请」动作：「先不去」只收起本页面里的提示；邀请 24 小时到期只由服务器结算，端到端没有测（60.75 不测）。
- `here.residents` 按区域标签而不是距离：站在区域边界两侧的两个人可能互相没有资料，卡片退化为名字和种类，下一次 `on_me` 补全。
- `invite` 服务器不去重，客户端靠 `invites.sent` 和本地记录挡；服务器去重留 P2。
- main 对 `notice` 不刷新 /me，所以本段订阅 `notice` 做去抖刷新。
- E 键对人不经过 `on_pick`（S4 可选补丁），「认识一下」按钮是键盘和手机的入口。

## 9. 真机待办（无头浏览器验证不了）

- 「去掉 invite 事件后的 refresh_me」：没有单独做；门牌可进靠 60.5 的 `data-can` 等待覆盖，但同一步里还有 notice 与打开面板的刷新，不一定只靠它。
- 限流、declined、too_far 的提示：断言都用服务器原文与 422 / 429 记录，没有改坏实现的反向验证。

## 11. 信里附的邀请（60.96）

A 用 API 给 B 寄一封附邀请的信（投递要 60 秒，放在 60.93 里，与截图重叠）。60.96：B 的信已投递但没读时，B 的 /me、Godot 一侧（fresh 为 0）、请柬栏、#actions 都没有这份邀请；B 回自己家用 API 读信后，/me 里出现 `via: "letter"` 的邀请；B 打开「人家」页签（触发一次 /me 刷新）后，Godot 一侧 fresh 为 1、请柬栏有一条新的、#actions 出现「去做客」。没有 invite 事件，所以也没有 toast。

## 12. 本次接手时清理掉的东西

接手时工作树里有三处未提交改动，其中两处是上一位同事做反向验证时留下的「改坏」（爱好名单 `reverse()`，`_reset_all` 少清爱好缓存），已撤掉；60.8 里「门牌上以字面量显示 A 的名字」的等待在浏览器里引用了 Node 侧的 `A`（ReferenceError 被 `until` 吞掉后表现为 20 秒超时），改成把 id 作为参数传进去。
